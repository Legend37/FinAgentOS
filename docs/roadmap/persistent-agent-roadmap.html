① 现状痛点：为什么 agent 现在"用不了"

🚫 完全无状态

每次刷新浏览器，姓名、年龄、风险偏好、自选 ticker 全部要重填。 后端 `/api/allocate` 是纯 stateless POST，没有 session、没有 user 概念。

🚫 历史对话不可见

SkillRecord 表里其实已经在沉淀教训（Critic APPROVE 时落盘）， ConversationTurn 表的 schema 也建好了，但根本没人调用—— state_manager.record_turn() 在生产链路里没被触发。

🚫 上次方案不能对比

PortfolioSnapshot 表里有 base_weights / final_weights， 但前端没有任何入口能看"我上次的配置是什么"。 "本周 vs 上周"对比、累计净值曲线、Sharpe 演化都没有。

🚫 不会主动复盘

"上次推荐你茅台 30%，过了 7 天表现如何"——agent 完全不会算这个。 没有"上次给的方案 vs 这 7 天真实行情"的归因分析（attribution）。

🚫 不会主动提醒

没有定时任务。用户主动来才有交互。理想状态：每周一早上系统主动推送 "你的组合本周 +1.2%，但新闻里 XX 政策可能利空你重仓的 A 资产，建议..."。

🚫 同一画像跨设备不连续

张三在手机上填完，回到电脑上又是新人——没有 user_id 串起来。 memory 系统里的 get_or_create_user(name) 只按"姓名"匹配，碰撞概率极高。

② 设计目标

关系延续
  • 一个用户 = 一个 user_id（持久 cookie + 可选邮箱登录）
  • 所有历史对话按 session 分组、可回溯
  • agent 每次开口前先 recall 最近 N 轮 + skill 库 + 最近一次快照
主动建议
  • 每 7 天 cron 检查每个 user：行情变化 / 重大新闻 / 风险偏离
  • 触发条件满足 → 自动生成"本周建议"并存入 PendingAdvice 表
  • 用户下次打开页面看到"📬 你有一份新建议"提示
归因复盘
  • 每份方案落 PortfolioSnapshot 时记录"建议日"
  • 下次咨询时用 7 天后行情算"如果当时听了我，现在如何"
  • 展示净值曲线 + 各资产贡献度 + 建议命中率

⚠️ 风险与注意事项

  • 多用户隔离：[[doc-update-on-big-changes]] memory 提到当前 state_manager 按 name upsert，碰撞风险高。改成 uuid 索引后必须迁移现有 SkillRecord 的 profile_signature。
  • 对话历史污染 prompt：召回 10 轮 ≈ 5000 token，加上 universe + 风险报告 + 新闻可能超 reasoner 上下文。需要做"重要轮次保留"策略（用 _truncate 已有的字符截断不够，要按"轮次类型"留）。
  • 归因计算的现实可行性：用 yfinance / akshare 回查 7 天前到今天的真实价格，但虚拟币/美股可能受限于网络可达性。需要降级到"用 SkillRecord 推测"。
  • 净值回测(#16) / 归因复盘 依赖真实行情通道：二者共用 fetch_price_window（无离线兜底，不同于生成方案的 fetch_and_calculate），必须能访问 push2his.eastmoney.com 行情 API。实测某些网络下该 API 被 RST（主页可达、量化接口连接重置，走/不走代理都失败）→ 返回空 → 前端「暂无法回测 / 等待数据积累」。是数据可达性问题，非代码 bug，逻辑以 mock 单测覆盖（回测 6 + 归因 4 全过）。须在能直连 eastmoney 行情 API 的环境运行；Clash 等代理需让 A 股行情走直连。
  • cron 进程：建议用 APScheduler 内嵌在 FastAPI 进程里（最简），不建议另起一个独立进程（运维复杂）。
  • 用户主动 vs 被动：建议第一版只支持"用户打开页面才生成新建议"，不真的发邮件/推送。先验证产品逻辑，再做通知通道。
  • 前后端耦合规则：见 [[frontend-backend-coupling]]——新 API 字段必须前端同步加渲染逻辑，否则等于没做。
